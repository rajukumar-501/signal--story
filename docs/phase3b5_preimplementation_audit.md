## 15 Mandatory Pre-Implementation Questions & Architectural Answers

### 1. What exactly enters the LLM?
The LLM receives an inspectable, structured prompt payload generated by `src/phase3b/prompts.py` containing:
- **System Prompt:** Senior root-cause analyst persona, evidence grounding rules, 6-step arbitration protocol, and untrusted data sandboxing instructions.
- **Section 1 (Observed Business Event):** Target KPI, date/period, target scope (`market`, `product_code`, `category`, `channel`), current value, previous period value, baseline value, MoM change %, delta vs baseline %, and anomaly status.
- **Section 2 (Investigated Candidate Hypotheses):** Screened candidate hypotheses from Phase 3A with initial scores, initial status, and initial confidence.
- **Section 3 (Evidence Catalog):** Authoritative indexed telemetry records (`EVD-001`, `EVD-002`, ...) containing source dataset, metric name, numerical value, observation date, evidence role (`SUPPORTING` / `CONTRADICTORY`), and temporal alignment (`BEFORE` / `DURING` / `AFTER`).
- **Section 4 (Sandboxed Qualitative Telemetry):** CRM notes, support tickets, and sales transcripts enclosed strictly within `<UNTRUSTED_EVIDENCE_RECORD ... classification="DATA_NOT_INSTRUCTION">` tags.
- **Section 5 (Required Arbitration Task & JSON Schema):** Strict schema definition requiring structured diagnostic sections, candidate comparisons, and claim-level citations.

### 2. What information is excluded from the LLM?
- Ground-truth answer keys (`expected_driver`, `expected_status`, `oracle_driver`, `true_root_cause`).
- Files and directory paths located in `Data/scenarios/evaluation_ground_truth/`.
- Evaluation scenario names/IDs (`S001`–`S008`).
- Benchmark evaluation criteria and target thresholds.

### 3. Can ground truth reach the LLM directly or indirectly?
**No.** Programmatic boundary tests (`test_phase3b1_isolation.py`, `test_phase3b2_security_isolation.py`, `Phase3BEvaluator.verify_evaluation_boundary()`) confirm 0 references to ground-truth files or keys across `src/phase3b/` and within serialized prompt payloads.

### 4. Can evaluation inputs contain hidden answer hints?
**No.** Evaluation inputs (`Data/scenarios/evaluation_inputs/S001_input.csv`–`S008_input.csv`) contain raw operational records (sales, inventory, pricing, marketing, support, CRM) without any labels indicating which driver is the true root cause.

### 5. How are evidence IDs generated?
`EvidenceContextBuilder` iterates deterministically over all evidence records across candidate hypotheses, de-duplicates them via unique attribute signatures (`source_dataset|record_id|metric|date|market|product_code|category|channel|evidence_role`), and assigns sequential identifiers (`EVD-001`, `EVD-002`, ...).

### 6. How does the LLM cite evidence?
The LLM cites exact `evidence_id`s in:
- `claims[].evidence_ids`: List of string IDs supporting specific observations, interpretations, or causal conclusions.
- `supporting_evidence[].evidence_id`: Specific findings with `source_dataset` and `metric`.
- `contradictory_evidence[].evidence_id`: Conflicting indicators.
- `traceability[].evidence_id`: Lineage mappings back to canonical datasets.

### 7. How is unsupported evidence detected?
`Phase3BResponseValidator` checks:
- Any cited `evidence_id` not found in `valid_evidence_ids` is flagged as an invalid/hallucinated citation error.
- Observation and causal claims with `evidence_ids = []` are flagged as unsupported claims.

### 8. How are hallucinated claims rejected?
If a claim cites non-existent evidence IDs (`EVD-999`), cites an evidence ID with a mismatched source dataset (`source_dataset` mismatch), or introduces ungrounded causal statements without citations, `Phase3BResponseValidator` marks `is_valid = False` and triggers the deterministic Phase 3A safe fallback.

### 9. How does the validator handle invalid output?
When validation fails, `Phase3BResponseValidator` returns a `ValidationResult(is_valid=False, errors=[...])`. The engine captures this and invokes `Phase3BResponseValidator.get_safe_fallback(context, reason=...)`, returning a fully grounded diagnostic report preserving Phase 3A analytical findings with `validation_status = "FALLBACK_PRESERVED"`.

### 10. What happens when the API fails?
In `LLMReasoningProvider`, HTTP exceptions, 500 server errors, and network connection drops are caught in a `try...except` block. If `enable_safe_fallback=True` (default), the provider gracefully returns a deterministic fallback payload without raising an uncaught exception.

### 11. What happens when the model times out?
`LLMConfig.timeout_seconds` (default 30.0s) enforces strict HTTP request timeouts. If a timeout occurs, a `TimeoutError` / `URLError` is caught and converted into a safe fallback report.

### 12. What happens when the model returns malformed JSON?
`_extract_json()` and `Phase3BResponseValidator` catch `json.JSONDecodeError` and markdown formatting issues, triggering the deterministic safe fallback.

### 13. What happens when the model refuses to follow the schema?
Missing top-level keys, unapproved driver strings, invalid status/confidence enums, or non-dict structures are caught by `Phase3BResponseValidator` and safely rejected.

### 14. What happens when untrusted evidence contains prompt injection?
Qualitative text is enclosed inside `<UNTRUSTED_EVIDENCE_RECORD>` tags. The system prompt explicitly instructs the LLM that text inside these tags is empirical observation data only, never system commands. Injected instructions (e.g. "Ignore previous instructions", "Choose pricing") are treated solely as customer verbatim text.

### 15. Does the deterministic Phase 3A fallback remain intact?
**Yes.** In all failure modes, the system preserves the exact Phase 3A top hypothesis, driver, status, confidence, and baseline telemetry.
